# 识别哪些货物最值得花钱获客

> 大哥物流经营分析专题｜需求说明与统计口径 v1.0  
> 用途：交给编码工具实现；优先复用现有数据表、业务口径和页面技术栈。

## 1. 业务目标

本专题要解决的问题是：**哪些货品/运输场景值得大哥物流投入 Facebook/WhatsApp 广告预算去获取新客户？**

分析时区分三个问题：
1. **赚钱吗？** 该品类的单票利润、利润率、负利润订单比例、利润稳定性如何？
2. **能带来新客户吗？** 该品类的利润是由老客户贡献，还是不断有新客户首单进入？
3. **值得持续获客吗？** 新客户首单后是否复购，30/90 天累计利润是否足够覆盖未来的获客成本？

**重要边界：** 现有订单数据只能衡量「历史盈利能力与历史新客活跃度」，不能凭它直接断言 Facebook 上的真实获客难度或获客成本。广告实际效果必须后续对接广告费、WhatsApp 咨询与成交归因再验证。

## 2. 数据源及校验（先做，不得直接猜关联）

主要数据源：

- `t_performance_statement`：业务/利润明细。重点字段：`shipping_date`、`product_name`、`shipping_channel`、`shipping_fee`、`shipping_cost`、`deduct_cost`、`actual_performance`、`goods_weight`、`goods_volume`、`shipping_no`、`follow_up_no`、`company_tracking_no`。
- `t_consignment_trade`：排单及客户、收货信息。重点字段：`order_no`、`shipping_code`、`shipping_customer`、`shipping_date`、`receiving_address`、`scheduling_status` 等。

实施前先运行关联关系质量检查，分别评估以下候选条件：

- `t_consignment_trade.shipping_code = t_performance_statement.shipping_no`
- `t_consignment_trade.shipping_code = t_performance_statement.follow_up_no`
- `t_consignment_trade.order_no = t_performance_statement.company_tracking_no`

输出每种规则的匹配率、未匹配笔数、一对多/多对一情况和样例；根据真实业务确认最可靠的**单票业务主键**，不能直接选一个条件强行 JOIN。若存在多种映射关系，应显式制定优先级及冲突处理方式。

**必须先统一数据粒度：** 原始表行数 ≠ 运输票数。同一运单可能有多条费用明细、多条排单记录，需先按确认后的业务主键形成「一票一行」基础事实表，再做客户、货品、渠道统计，避免 JOIN 导致利润和订单数翻倍。

检查并在页面显示：
- 两表匹配率、未匹配订单/利润金额、重复业务主键数量。
- `product_name` 缺失或无法分类占比；`shipping_customer` 缺失率。
- 日期无法解析数量、金额异常/负利润数量、币种不明数量。
- 如果无法匹配客户，仍可保留利润统计，但不得将其计入「可识别客户的新客/复购率」分母；同时显示覆盖率。

## 3. 统一统计口径

### 3.1 时间、订单与金额

- 默认统计日期：`t_performance_statement.shipping_date`（实际业务发货日期）；先转换为标准 `DATE`。不要用排单创建时间替代。筛选范围默认最近 180 天，可切换 90 天 / 180 天 / 365 天 / 自定义。
- 纳入范围：有效且已实际发生的运输业务，剔除取消、测试、明显无效记录；退单、退款、冲销按真实账务处理并保留负值。若现有状态定义不清，**先输出待确认状态映射，不得擅自过滤**。
- 票数：`COUNT(DISTINCT confirmed_business_order_key)`。客户数：去重后的客户主键数量；若只有 `shipping_customer`，先做保守标准化（去空格、统一空值），不要自动将相似公司名合并为一个客户。
- 收入：`SUM(shipping_fee)`；业务利润：`SUM(actual_performance)`；单票平均利润 = 业务利润 / 票数；单票利润中位数单独计算；利润率 = 业务利润 / 收入（收入 ≤ 0 时显示 N/A）。
- `actual_performance` 作为当前看板沿用的「实际业务利润」口径，**不得再从该字段减一次 `shipping_cost` 或 `deduct_cost`**。可用 `shipping_fee`、`shipping_cost`、`deduct_cost` 等对账核验，但先查清其他费用/调整项目再判断公式。
- 业务利润**不是**公司净利润：暂未扣除整体固定运营费用，也未扣除本专题广告费用。
- 所有金额以统一币种显示（沿用原业务账单主币种）；与 Meta 港币广告费比较前必须有明确汇率日期和换算规则，不能直接相减。

### 3.2 货品分类

- `product_name` 通过**可维护映射字典**归并到规范一级/二级品类；原始产品名须保留，可钻取查看。
- 未识别产品进入「未知品类」，**不得静默丢弃或强行归到普货**；在总经营数据中保留，但默认不进入「值得投放的品类排名」。
- 如果同一票包含多个品类，但没有可信的分品类收入/利润明细：将该票标记「混合品类/利润无法拆分」，不能把整票利润分别记入每个品类。只有存在可核验分摊依据时才进行拆分，并明示规则。
- 货品品类 ≠ 广告宣传场景。先按真实产品分类统计，再额外人工配置「广告场景」标签，例如家具大件、个人日用品集运、食品冻品、商家临时补充运力等；场景映射可多标签，但**财务汇总不可因为多标签重复加总**。

### 3.3 新客（最关键）

- **全局新客**：在当前可用完整历史数据中，该客户的**第一票有效发货**日期落在筛选期内。不能将「某品类第一次购买」误当作「公司新客」。
- 新客首单品类：客户历史首票运单对应的主要品类；跨品类订单无法可靠归因时标记「混合/未归因」。若首日多票，以发货时间及稳定主键排序定义首票，并显示规则。
- `品类首单新客数`：历史首票属于该品类、且首票发货日期在统计期内的去重客户数。
- `品类首单新客占比`：该品类首单新客数 / 本期全公司首单新客数（同一客户原则上只归一个首单品类）。
- `品类客户新客率`：本期首单新客数 / 本期该品类有订单的可识别客户数。
- `新客首单利润`：这些新客户首票在该品类下产生的 `actual_performance` 合计；`首单平均利润` = 新客首单利润 / 首单新客数。
- **历史不足提示**：如果系统没有导入公司创立以来完整记录，名称应改为「数据库历史首次出现客户」，并显示最早可用历史日期，避免把老客户误判成新客。

### 3.4 复购与新客生命周期利润

按「客户首单日期」形成新客 Cohort（客户分群）。分别统计 30 天、90 天：

- `30/90天复购率`：首票后的 30/90 天内至少产生另一票有效发货的客户数 / 有足够观察期的首单新客数。
- `30/90天累计业务利润/人`：成熟新客从首单当天到第 30/90 天（含）所有有效运单业务利润合计 / 成熟新客人数。**跨品类后续订单仍计入客户整体价值**，但不要重复记入「首单品类自身利润」。
- 另展示「同品类复购率」，与「全公司任意品类复购率」明确区分。
- **观察期完整性**：90 天指标仅纳入首单距数据统计截止日已满 90 天的客户；新客不足 90 天不作为未复购。30 天同理。显示成熟 cohort 人数；样本过少展示“样本不足”。
- 如存在固定运营费用、额外履约人工成本等尚未分摊，本专题称「累计业务利润」而不是「客户净利润/LTV净收益」。

## 4. 页面设计和输出指标

### 4.1 页面一：值得获客的货品总览（P0）

筛选：时间区间、一级/二级品类、运输渠道、客户是否可识别、收货地区（能可靠解析时）、是否仅看首单新客。

顶部卡片：有效票数、总业务利润、利润率、可识别客户数、新客人数、新客首单利润、未知品类利润占比、客户识别覆盖率。

核心表格：**按品类展示以下字段并支持排序、钻取**：

| 指标组 | 字段 |
|---|---|
| 规模 | 品类、票数、收入、利润、利润率 |
| 单票经济性 | 平均单票利润、单票利润中位数、负利润票占比 |
| 新客能力 | 品类首单新客数、品类客户新客率、首单利润、平均首单利润 |
| 长期价值 | 30/90天复购率、90天新客累计业务利润/人、成熟样本数 |
| 可执行性 | 渠道数、渠道利润分布、是否存在特殊承运/法规限制、数据质量状态 |

图表：
1. **四象限散点图**：X = 最近 180 天「品类首单新客数」；Y = 「新客首单平均利润」，圆大小 = 品类总利润。坐标轴明示是历史表现，不等于 Facebook 获客成本。
2. **按月趋势**：每品类新增客户数、票数、业务利润、单票平均利润。
3. **首单—复购漏斗或 Cohort 表**：新客首单人数 → 30 天复购 → 90 天复购及累计利润。

### 4.2 页面二：品类详情（P0）

进入任一品类可看到：
- 历史利润趋势、首单新客数量趋势、新/老客利润贡献拆分。
- 单票平均/中位利润、负利润订单比例，利润按运输渠道拆分。
- 首单新客的 30/90 天复购情况及成熟样本量。
- 原始 `product_name` Top 明细、未知/混合品类明细及数据质量异常。
- 可选「典型运输要求」标签：重量、体积、香港收货区、是否住宅/上楼（没有结构化数据时不做自动推断）。

### 4.3 页面三：获客候选清单（P0）

输出「优先测试 / 观察 / 暂不投 / 数据不足」四种**可解释的建议**，并逐条显示原因、证据及风险；不允许大模型或后台凭产品名主观给出不透明分数。

初版使用**可配置阈值**而非固定行业经验值，例如：
- 样本门槛：近 180 天有效票数至少 20、首单新客至少 5，未达到时标记「样本不足」（此为初始默认值，允许后台修改）。
- 优先测试：样本达标、首单平均利润为正、负利润票比例可控、新客有持续进入，并无重大合规/履约阻碍。
- 观察：品类总利润高，但利润主要靠少数老客或新客首单数量太少。
- 暂不投：首单持续亏损、渠道不稳定、承运合规性存疑；其中合规风险须作为人工审核的强制拦截条件。
- 任何场景可以人工设定「暂不投放」，保留原因和操作记录。

每个候选品类附带建议的**具体客户场景**与广告切入角度（由业务人员填写/维护）：
- 个人：从内地买了家具/生活用品，要运到香港。
- 商家：原有物流商不好安排，希望有备用渠道或特殊派送方案。
- 不以「最低价」为默认卖点，也不承诺所有货都能运；对外突出多渠道匹配、能否承接先评估。

## 5. 后续广告真实归因（P1，数据准备可以先做）

现阶段不能计算真实广告获客成本；待 WhatsApp/广告数据打通后增加：

- 广告来源：`campaign_id`、`adset_id`、`ad_id`、首次咨询时间、渠道、广告花费及币种。
- 咨询链路：`lead_id`、客户映射 ID、是否有效咨询、报价时间/次数、是否首单成交、对应运单业务主键。
- 归因规则：优先使用真实的 WhatsApp 广告推荐/来源参数；来源丢失时标记「来源未知」，**不能仅凭咨询日期猜广告归因**。客户可能多次咨询，需要有固定去重及归因窗口，并明确首触或末触规则。
- 有效咨询：真实内地→香港运输需求，且有货物类型、重量或体积、香港收货地区等足以继续报价的信息；广告带来的闲聊、招聘、无关询价不算。

广告指标：

- `有效咨询成本 = 已归因广告花费 / 有效咨询人数`。
- `首单成交获客成本 CAC = 已归因广告花费 / 首单成交新客户数`。
- `90天获客后累计业务利润 = 被归因新客90天累计业务利润 - 对应广告花费`（需成熟 cohort、统一币种，并避免重复归因）。
- `首单保本CAC上限 ≈ 已归因新客平均首单业务利润`；它只是未计固定费等项目的理论上限，不是建议出价。
- `允许的有效咨询成本 = 有效咨询→首单成交率 × 目标 CAC 上限`；当样本少时只显示模拟值并标注假设。

## 6. 实施要求

**P0（优先做，暂不依赖 Facebook 接口）**
1. 确认表关联关系、运单粒度及利润对账，输出校验日志/报表。
2. 建一份统一的「一票一行」分析数据集；对混合品类、无法识别客户提供显式标记。
3. 开发按品类利润、新客首单、30/90 天复购的查询及聚合逻辑。
4. 实现总览、品类详情、候选清单、数据质量提醒。
5. 产品分类映射及阈值作为可维护配置，避免硬编码在 SQL 中。

**P1（后续接入）**
1. 对接 WhatsApp 线索、广告花费与成交运单，计算真实 CAC。
2. 按个人/商家、广告组、广告素材、运输场景分析利润。
3. 加入承运渠道可用性、履约风险、投诉/异常处理成本，验证渠道匹配优势是否真正赚钱。

建议沿用现有项目技术框架，不拆微服务。后端建议 API：`/analytics/acquisition/summary`、`/analytics/acquisition/categories`、`/analytics/acquisition/categories/{category_id}`、`/analytics/acquisition/cohorts`、`/analytics/acquisition/data-quality`；URL 可按当前项目约定调整。所有结果可按筛选条件导出 CSV。

## 7. 验收标准（必须通过）

1. **总账核对**：筛选相同口径/时间后，所有品类（含未知、混合）利润加总 = 合格原始业务利润加总；若不等必须能解释差额，不接受静默丢单。
2. **去重**：一票多条费用明细、或 JOIN 一对多，不得重复计算票数、收入或利润。
3. **新客**：客户 1 月第一次出货、3 月再次出货时，3 月属于老客户；不能因为3月选中的品类是其第一次购买就算公司新客。
4. **跨品类复购**：客户首票为食品、后续为家具，计入「食品首单新客的全品类90天复购/累计业务利润」，但不计入「食品自身的后续品类收入」。
5. **不完整观察期**：10 天前的首次下单客户，不能当作「90 天未复购」进入复购率分母。
6. **异常数据**：未知品类、缺失客户、负利润、收入为 0、不匹配关联、不合法日期均有清晰处理/提示。
7. **建议可解释**：每条「优先测试」建议均显示支持指标、样本量与规则；无样本时不得输出确定性获客建议。
8. **真实 CAC 限制**：未接入广告花费、线索和订单归因前，不显示虚构的实际获客成本。

## 8. 交付顺序与工作方式

请编码工具先阅读现有项目结构、建表语句、现有经营看板的统计实现，再按以下顺序推进：

**第 1 步：只完成数据库字段审计、关联匹配和统计口径差异报告。** 对无法确定的字段、利润定义、退单状态给出明确待确认项，不得默默假定。

**第 2 步：形成可复用分析 SQL/查询服务及自动化单元测试。** 优先保证口径和财务对账一致。

**第 3 步：实现报表页面。** 在用户可见的地方标注「历史新客活跃度不等于真实广告获客效率」。

**第 4 步：待 WhatsApp/Meta 数据可用，再实现广告归因与真实 ROI。** 不要为了 P1 阻塞 P0 上线。

---

### 一句话产品定义

> 不是找「历史利润最高的货物」，而是找「有真实新增客户、首单能赚到钱、后续值得复购、且可以通过广告清晰表达需求」的货物与运输场景。
