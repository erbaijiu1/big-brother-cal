# Facebook 获客分析：字段审计与统计口径差异报告

> 审计日期：2026-10-26  
> 环境：本地 `db_prize_cal`  
> 本阶段范围：只读字段审计、关联关系验证、统计口径设计；未新增或修改数据库结构。

## 1. Requirements Clarification

### 已确认目标

新增一个独立的“获客机会”分析专题，用历史订单回答：哪些货品有真实新客进入、首单能赚钱、后续会复购，适合优先做 Facebook 广告测试。

页面必须明确区分：

- 历史盈利能力，不等于 Facebook 实际获客成本。
- 数据库历史首次出现客户，不等于公司成立以来真正的新客户。
- 业务毛利润，不等于扣除固定成本和广告费后的公司净利润。

### 已确认实施约束

1. 利润沿用经营看板：`shipping_fee - shipping_cost`；缺成本订单保留订单和收入，排除利润分子、分母，并展示覆盖率。
2. V1 使用八个规范一级品类：冻品、熟食、水果、酒类、食品、生鲜肉类、水产海鲜、普货。
3. 2,943 个历史原始品名只做 dry-run；无法识别保留 `UNKNOWN`，数据库回填另行提交 SQL 审批。
4. 以绩效发货记录为统计基础，不擅自按排单状态过滤；取消、退款、冲销、重复和赔付仅作审计告警。
5. 客户严格使用 `company_tracking_no = order_no` 一对一关联，不使用 `shipping_no` 回退。

## 2. Requirements Analysis

### 2.1 功能拆分

产品需求 → 页面/模块 → 变更点：

1. 哪些货值得获客 → 获客机会总览 → 指标卡、四象限、品类排行、数据质量提示。
2. 为什么值得投 → 品类详情 → 月度趋势、新老客贡献、渠道、负利润、30/90 天 cohort。
3. 是否应该投 → 候选清单 → 使用透明阈值输出“值得测试/需要观察/暂不建议投放”。
4. 是否相信数据 → 数据质量抽屉 → 关联覆盖、未知品类、缺成本、负利润、历史起点。
5. 业务调整 → 配置模块 → 品类映射、候选阈值、人工合规拦截与广告场景说明。

### 2.2 用户路径

1. 管理员进入独立“获客机会”页面。
2. 默认查看最近 180 天，并看到历史数据边界与质量告警。
3. 从四象限或候选清单选择一个品类。
4. 进入品类详情，检查首单利润、负利润率、新客数、成熟 cohort、30/90 天复购。
5. 结合人工维护的承运限制和广告场景，决定是否小额测试广告。
6. 后续接入 Meta/WhatsApp 归因后，再比较真实 CAC；P0 不展示虚构 CAC。

### 2.3 页面操作规格

- 切换时间范围 + 任意有效范围 + 全部指标 → 使用相同的一票一行事实集重新计算。
- 点击品类 + 品类存在 + 排行行/散点 → 打开该品类详情。
- 查看建议 + 样本不足 + 候选行 → 显示“数据不足”，不得输出确定性建议。
- 查看复购 + 观察期不完整 + cohort → 不进入 30/90 天分母，并显示成熟样本数。
- 查看未知品类 + 无规范映射 + 数据质量 → 保留收入和利润，但默认排除投放排名。
- 查看客户指标 + 无可靠客户关联 + 订单 → 保留财务指标，不进入新客和复购分母。

### 3.2 三种候选关联关系

| 关联规则 | 匹配绩效行 | 未匹配 | JOIN 后行数 | 重复/冲突 | 判断 |
| --- | ---: | ---: | ---: | --- | --- |
| `shipping_code = shipping_no` | 13,859 | 101 | 348,318 | 1,710 个多对多键 | 不可直接 JOIN |
| `shipping_code = follow_up_no` | 8,646 | 5,323 | 260,634 | 417 个多对多键 | 不可作为客户主关联 |
| `order_no = company_tracking_no` | 13,134 | 840 | 13,134 | 无重复，严格一对一 | 推荐主关联 |

`shipping_no` 并非一票主键。例：`SA32` 在 2025-06 至 2026-09 期间出现 202 个绩效订单、172 个发货日期，对应长期客户代码。使用它关联会将同一客户跨日期订单相互笛卡尔扩张。

推荐规则：

```text
order_key = performance.company_tracking_no
customer join = trade.order_no = order_key
无法精确匹配时：财务数据保留，客户、新客、复购指标排除
不使用 shipping_no/follow_up_no 做模糊回退
```

唯一键回退审计显示：在 840 个主关联未匹配行中，`shipping_no` 双侧都唯一的仅 2 行，收益很小；`follow_up_no` 在重叠样本中还出现 10 个客户冲突，因此不建议回退。

## 4. Technical Specification Design

### 4.1 推荐架构

不拆微服务，在现有 `cal_price_server` 和 uni-app 管理后台中新增专题：

```text
t_performance_statement（一票一行财务事实）
        + 精确 LEFT JOIN
t_consignment_trade（客户/地址）
        + 可维护映射
规范一级品类/广告场景/阈值配置
        ↓
acquisition analytics query service
        ↓
总览 / 品类详情 / 候选清单 / 数据质量
```

基础事实集原则：

```text
一票主键 = company_tracking_no
客户主键 = TRIM(shipping_customer)，仅限精确关联成功记录
日期 = performance.shipping_date
收入 = shipping_fee
毛利润 = shipping_fee - shipping_cost
缺成本 = shipping_fee > 0 AND shipping_cost = 0
缺成本订单保留规模指标，但不进入利润相关分子/分母
```

### 4.2 页面方案比较

| 方案 | 描述 | 优点 | 缺点 | 适用性 |
| --- | --- | --- | --- | --- |
| 塞入现有经营统计 | 在当前页面增加获客模块 | 少一个入口 | 页面已经信息密集，利润分析与投放决策混在一起 | 不推荐 |
| 独立“获客机会”页面 | 独立总览，详情作为子页面/抽屉 | 目标明确，筛选和解释空间足够 | 新增两个路由和接口 | 推荐 |
| 三个完全独立页面 | 总览、详情、候选各自独立 | 模块边界清楚 | 首版导航复杂、重复筛选状态多 | 后续数据成熟再拆 |

推荐首版：一个独立“获客机会”总览页，包含四象限、品类表和候选分组；点击品类进入独立详情页。数据质量使用抽屉，不再单独占页面。

### 4.3 API 设计

- `GET /cal_price/acquisition/overview`
- `GET /cal_price/acquisition/categories`
- `GET /cal_price/acquisition/categories/{category}`
- `GET /cal_price/acquisition/cohorts`
- `GET /cal_price/acquisition/data-quality`
- `GET /cal_price/acquisition/orders`

所有接口共享筛选对象：开始/结束日期、一级品类、运输渠道、客户可识别状态。总览和排行必须来自同一个事实集，避免口径漂移。

## 5. Component / Module Design

### 后端

- `AcquisitionFactQuery`：一票一行事实集、客户精确关联、数据质量标记。
- `CustomerCohortService`：全局首单、30/90 天成熟 cohort、跨品类复购。
- `CategoryMetricsService`：规模、利润、负利润、首单新客、渠道分布。
- `CandidateRuleEngine`：读取配置阈值，输出建议状态、证据和风险，不使用黑盒评分。
- `AcquisitionAuditService`：关联覆盖、未知品类、缺成本、历史边界。

### 前端

- `AcquisitionOverviewPage`：筛选、指标卡、四象限、候选清单。
- `CategoryOpportunityTable`：多指标排序和钻取。
- `AcquisitionQuadrant`：历史新客数 × 首单平均毛利润，圆大小为品类毛利润。
- `CohortPanel`：30/90 天成熟样本、复购率、累计业务毛利润/人。
- `DataQualityDrawer`：覆盖率和口径告警。
- `CategoryDetailPage`：趋势、新老客贡献、渠道、原始品名和异常订单。

## 6. Risk and Boundary Analysis

- 历史只覆盖 2025-01 以后，必须使用“数据库历史首次出现客户”措辞。
- 6% 绩效订单无法可靠识别客户，不能进入新客/复购分母。
- 61.3% 订单尚未归一到一级品类，先补映射才能上线可靠排名。
- 缺成本记录不得产生 100% 毛利假象。
- 同日多票首单需用 `shipping_date + company_tracking_no` 稳定排序，但 DATE 没有时分秒，首日多票归因仍存在人为规则。
- 当前没有币种字段，不能与港币 Meta 广告费直接比较。
- 当前没有广告归因字段，P0 只能给“广告测试候选”，不能显示实际 CAC 或 ROI。
- 状态字段缺少完整业务说明，首版不应擅自批量过滤历史绩效。

## 9. 复购与边界规则

- “数据库历史首次客户”和“品类首次客户”分别计算、分别展示，不互相替代。
- 首次出现时间从完整可用历史计算，不受页面筛选起点影响；当前历史起点为 2025-02-08，页面提示左截断风险。
- 30/90 天复购只把观察窗完整的去重客户放入分母。
- 任意品类复购和同品类复购同时展示。
- 同日多票按 `shipping_date → company_tracking_no → id` 稳定排序，首票之后的同日票视为后续订单。
- 客户无法精确识别的订单保留经营统计，但不进入首次客户和复购分析。
- 未知品名不默认归入普货；未经人工确认的 dry-run 结果不进入数据库。
